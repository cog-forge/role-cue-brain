3.5 Platform Administration & Governance

This section defines the administrative functions governing platform integrity, security, and quality, encompassing global user account oversight and locking, job posting content moderation, platform-wide interview session audit tracking, AI behavior prompt configuration, evaluation rubric calibration, and provider voice profile catalog curation.

3.5.1 User Account Governance & Security Locking

Function trigger: An Administrator navigates to the Account Governance section of the Admin Governance Console.

Function description: This function provides administrative oversight of all registered platform accounts across roles (Candidate, Recruiter, Administrator), enabling filtering by status and role, inspection of account details, and execution of security administrative actions to lock or unlock accounts.

Actor/roles: Administrator

Purpose: To enforce platform terms of service, protect system security, and suspend compromised or malicious accounts.

Interface: Web: Admin Governance Console, Account Governance (User List), Account Detail & Lock/Unlock

Data processing:

  • Input data: Account filter criteria (role, status, registration date), search keyword (name, email), target Account ID, lock/unlock command with administrative reason.
  • Output data: Filtered list of registered user accounts, detailed account dossier, updated account status flag (Active / Locked), security audit log entry.

Function details: Only users holding the Administrator role can access this capability (BR-35). When an account is locked, Better Auth session resolution immediately rejects any subsequent authentication attempts, and active sessions are terminated (BR-05). Administrators can subsequently unlock an account after verification.

Business rule: BR-05 (A locked account must not be allowed to log in or access protected functions), BR-35 (Only an Administrator can lock or unlock another user's account).

Normal case:

  1. The Administrator accesses the Admin Governance Console and opens Account Governance (User List).
  2. The system renders the registered accounts table with search, role filters, and status indicators (UC 41).
  3. The Administrator selects an account and navigates to Account Detail & Lock/Unlock.
  4. The Administrator clicks "Lock Account", enters a mandatory administrative rationale, and confirms.
  5. The system updates the account status to "Locked" (BR-05, BR-35), terminates active sessions, and logs the security audit event.

Abnormal case:

  • Non-admin access attempt: The system enforces strict role-based access control and denies entry.
  • Administrator attempts to lock their own active administrator account: The system prohibits self-lockout.

3.5.2 Job Posting Moderation & Platform Adjudication

Function trigger: An Administrator navigates to the Job Posting Moderation Queue.

Function description: This function provides content moderation oversight for recruiter-submitted job openings, allowing administrators to inspect vacancy details, AI competency models, and company interviewer configurations, and record formal approval or rejection decisions before publication.

Actor/roles: Administrator

Purpose: To verify that all job openings published on the platform meet professional quality, compliance, and non-discrimination standards.

Interface: Web: Job Posting Moderation Queue, Job Posting Review & Approval, Moderation Decision Dialog

Data processing:

  • Input data: Moderation status filter (Pending, Approved, Rejected), Job Posting ID, moderation decision (Approve/Reject), feedback notes.
  • Output data: Filtered moderation queue, comprehensive vacancy review view, updated Job Posting publication status, moderation notification to Recruiter.

Function details: When a Recruiter submits a job opening, it enters the queue in "Pending Moderation" status. The posting cannot be viewed by candidates or applied to until an Administrator approves it (BR-36, BR-46). If rejected, the Administrator provides actionable feedback, allowing the Recruiter to revise and re-submit.

Business rule: BR-36 (Only an Administrator can approve or reject Job Postings for platform moderation), BR-46 (A Job Posting must not be publicly available while its moderation status is pending or rejected).

Normal case:

  1. The Administrator opens the Job Posting Moderation Queue.
  2. The system displays pending recruiter job submissions (UC 43).
  3. The Administrator clicks a submission to open the Job Posting Review & Approval screen.
  4. The Administrator reviews the job description text, competency taxonomy, and selected interviewer avatar/voice.
  5. The Administrator clicks "Approve", opens the Moderation Decision Dialog, and confirms (UC 44).
  6. The system marks the posting as "Approved" (BR-36), publishes it to the Candidate Job Board (BR-46), and notifies the Recruiter.

Abnormal case:

  • Rejection without rationale: The system requires an explanatory moderation note before confirming rejection.

Screen layout: Screen Layout Reference: Job Posting Moderation Queue, Job Posting Review & Approval, Moderation Decision Dialog. Visual layout to be produced during the dedicated UI design phase.

3.5.3 Platform Interview Session Governance & Audit

Function trigger: An Administrator navigates to "Interview Sessions Oversight" within the governance console.

Function description: This function provides platform-wide audit visibility into all historical and active interview sessions across all users, enabling searching, filtering by date and outcome, and inspecting full session execution details including transcript turns and rubric evaluations.

Actor/roles: Administrator

Purpose: To monitor platform simulation quality, investigate technical or scoring anomalies, and audit system integrity.

Interface: Web: Interview Sessions Oversight, Interview Session Detail

Data processing:

  • Input data: Filter criteria (User ID, date range, session state: Completed/Abandoned/Evaluating, overall score range), selected Session ID.
  • Output data: Filtered list of platform interview sessions, comprehensive session audit dossier (blueprint reference, timestamps, transcript turns, score vectors).

Function details: Administrators possess read-only audit access across all candidate practice sessions and recruitment screening sessions. The audit view binds the session to the exact internal Blueprint and evaluation criteria version active at session execution time (BR-24).

Business rule: BR-24 (Evaluation of a completed Interview Session must remain associated with the Blueprint and criteria active when the session was created).

Normal case:

  1. The Administrator navigates to Interview Sessions Oversight.
  2. The system renders the global interview sessions ledger with comprehensive search and filtering controls (UC 50).
  3. The Administrator filters by date range or session status.
  4. The Administrator clicks a session row to inspect its full execution dossier on the Interview Session Detail screen (UC 51).
  5. The system displays dialogue transcripts, turn timings, avatar and voice metadata, and evaluation scoring breakdowns (BR-24).

Abnormal case:

  • Session ID not found: System returns an error and redirects to the sessions list.

Screen layout: Screen Layout Reference: Interview Sessions Oversight, Interview Session Detail. Visual layout to be produced during the dedicated UI design phase.

3.5.4 AI Behaviour & Evaluation Criteria Calibration

Function trigger: An Administrator navigates to "AI Behaviour Management" or "Evaluation Criteria Calibration" within the Interview Feature Configuration module.

Function description: This function enables administrators to calibrate global AI interviewer behavioral prompts, configure interview dialogue constraints, and edit the global evaluation rubrics and scoring weights used to assess candidate technical competencies.

Actor/roles: Administrator

Purpose: To fine-tune the conversational realism of the AI interviewer and maintain rigorous, standardized competency assessment rubrics across the platform.

Interface: Web: Interview Feature Configuration, AI Behaviour Management, Prompt Template Editor Drawer, Evaluation Criteria Calibration, Rubric Template Editor Drawer

Data processing:

  • Input data: Global behavioral prompt templates, dialogue turn limits, pacing parameters, evaluation rubric dimensions, scoring weight distributions.
  • Output data: Versioned prompt template configurations, updated global evaluation rubric definitions, calibration audit log.

Function details: Only Administrators can modify evaluation rubrics and AI behavior prompts (BR-37, BR-38). Changes take effect for newly initiated interview sessions while preserving historical consistency for completed sessions. The Prompt Template Editor Drawer allows adjusting interviewer tone and follow-up strictness, while the Rubric Template Editor Drawer allows calibrating criteria weighting (e.g., technical correctness, architecture design, clarity).

Business rule: BR-37 (Only an Administrator can edit global Evaluation Criteria), BR-38 (Only an Administrator can manage platform AI Behaviour and interview-feature configurations).

Normal case:

  1. The Administrator accesses AI Behaviour Management and opens the Prompt Template Editor Drawer (UC 46).
  2. The Administrator adjusts interviewer conversational behavior instructions and saves changes.
  3. The Administrator opens Evaluation Criteria Calibration and launches the Rubric Template Editor Drawer (UC 45).
  4. The Administrator updates competency weighting parameters and confirms validation checks.
  5. The system saves the calibrated rubric version (BR-37, BR-38) and applies it to subsequent interview sessions.

Abnormal case:

  • Scoring weights do not sum to 100%: The system flags the validation discrepancy and prevents saving until weights are balanced.

Screen layout: Screen Layout Reference: Interview Feature Configuration, AI Behaviour Management, Prompt Template Editor Drawer, Evaluation Criteria Calibration, Rubric Template Editor Drawer. Visual layout to be produced during the dedicated UI design phase.

3.5.5 Provider Voice Profile Catalog Management

Function trigger: An Administrator navigates to the Voice Profile Catalog in the governance console.

Function description: This function manages the catalog of available text-to-speech voice profiles by fetching external voice assets from the connected provider (e.g., ElevenLabs), cataloging voice metadata (gender, accent, language), and deprecating or removing outdated voice profiles.

Actor/roles: Administrator, External TTS Provider (ElevenLabs)

Purpose: To curate a high-quality selection of realistic voices available for candidate practice and recruiter job opening configurations.

Interface: Web: Voice Profile Catalog, Fetch Voice Profiles Modal, Delete Voice Profile Dialog

Data processing:

  • Input data: Fetch provider trigger, provider API synchronization parameters, Voice Profile ID selected for deletion/deactivation.
  • Output data: Synchronized voice catalog list, updated voice metadata records, deletion confirmation.

Function details: Administrators manage provider-sourced Voice Profiles (BR-39). In accordance with ratified product scope, Administrators do NOT manage candidate 3D avatars or virtual room backgrounds (BR-40). Fetching voices queries the external TTS provider and registers available voice IDs. Deleting a voice profile marks it as unavailable for future sessions while preserving historical references in completed interview logs.

Business rule: BR-39 (Only an Administrator can fetch, view, or delete provider-sourced Voice Profiles), BR-40 (Administrators must not manage Candidate Personal 3D Avatar assets or the platform 3D background catalog).

Normal case:

  1. The Administrator navigates to the Voice Profile Catalog.
  2. The system displays all registered voice profiles with name, provider ID, accent, and sample audio playback (UC 47).
  3. The Administrator clicks "Fetch Voice Profiles", opening the Fetch Voice Profiles Modal (UC 48).
  4. The system queries the external TTS provider API, identifies newly available voices, and synchronizes the catalog.
  5. (Optional) The Administrator selects an obsolete voice profile, clicks "Delete", and confirms via the Delete Voice Profile Dialog (UC 49).
  6. The system removes or deactivates the voice profile (BR-39).

Abnormal case:

  • Provider API connection timeout: The system displays a connectivity alert and retains the existing voice catalog without corruption.
  • Attempting to delete a voice currently configured on an active published job posting: The system warns the Administrator and requires reassignment or soft-deprecation.

Screen layout: Screen Layout Reference: Voice Profile Catalog, Fetch Voice Profiles Modal, Delete Voice Profile Dialog. Visual layout to be produced during the dedicated UI design phase.
