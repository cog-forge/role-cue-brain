3.2 Account & Access Management

This section defines the functional requirements for user registration, identity authentication, credential recovery, user profile management, credential security, and multi-factor authentication across all platform user roles.

3.2.1 Platform Public Exploration & Value Proposition

Function trigger: A Guest accesses the platform root URL via a web browser.

Function description: This function renders the public marketing and platform introduction portal, showcasing the RoleCue value proposition, technical interview simulation capabilities, supported industry domains, and navigation paths for account registration and authentication.

Actor/roles: Guest

Purpose: To introduce prospective candidates and recruiters to the platform's AI-driven technical interview features and facilitate user onboarding.

Interface: Web: Public Landing Page

Data processing:

  • Input data: Public catalog highlights, feature overview assets.
  • Output data: Rendered public landing view, product overview summaries, navigation links to registration and login.

Function details: The interface operates publicly without requiring prior authentication. It presents overview highlights regarding real-time 3D interviewer interaction, job description analysis, automated rubric-based scoring, and recruiting capabilities.

Business rule: BR-04 (A user must be authenticated before accessing registered-user features; unauthenticated guests may only view public marketing content and entry points).

Normal case:

  1. The Guest navigates to the platform base URL.
  2. The system loads and displays the Public Landing Page with feature highlights, value propositions, and role-based onboarding calls to action.
  3. The Guest clicks the registration or login call to action to transition to the respective authentication interface.

Abnormal case:

  • Network connectivity failure prevents assets from loading; the client renders an offline retry notice.

Screen layout: Screen Layout Reference: Public Landing Page. Visual layout to be produced during the dedicated UI design phase.

3.2.2 User Registration & Role Selection

Function trigger: A Guest clicks the "Sign Up" or "Register" button on the Public Landing Page or login view.

Function description: This function captures account registration credentials, validates email uniqueness and password complexity, establishes the initial user identity record, and dispatches an email verification notice.

Actor/roles: Guest

Purpose: To allow new candidates and recruiters to establish authenticated accounts with verified identities and defined roles.

Interface: Web: Account Registration, Email Verification Notice

Data processing:

  • Input data: Full name, email address, password, password confirmation, desired account role (Candidate or Recruiter).
  • Output data: Newly created user account record with pending verification status, dispatched verification token, and confirmation screen.

Function details: Registration validates that the provided email is not already associated with an existing account. The system validates password strength according to platform security policy. Better Auth manages the underlying credential generation and token creation, while the interface transitions the user to the Email Verification Notice screen.

Business rule: BR-01 (An account must have a unique email address), BR-02 (An account password must be between 8 and 32 characters long), BR-03 (An account password must contain at least one lowercase letter, one uppercase letter, one number, and one special character).

Normal case:

  1. The Guest navigates to the Account Registration screen.
  2. The Guest inputs their full name, email address, password, password confirmation, and selects their role.
  3. The system validates that the email address is unique and the password complies with security rules.
  4. The system registers the account in a pending verification state and sends an email containing an activation link.
  5. The system redirects the user to the Email Verification Notice screen with instructions to check their inbox.

Abnormal case:

  • Duplicate email address: The system informs the user that an account with this email already exists and offers a link to login or recover the password (BR-01).
  • Password complexity violation: The system indicates the specific unmet requirements (length, case, numeric, or special character) and prevents submission (BR-02, BR-03).
  • Confirmation password mismatch: The system flags the mismatch and prompts the user to re-enter matching passwords.

Screen layout: Screen Layout Reference: Account Registration, Email Verification Notice. Visual layout to be produced during the dedicated UI design phase.

3.2.3 User Authentication & Session Resolution

Function trigger: A user submits login credentials on the Account Login screen, or clicks the "Sign Out" action from the authenticated navigation bar.

Function description: This function verifies user identity via email and password credentials, checks account status against governance restrictions, prompts for two-factor authentication if enabled, resolves an authenticated session, and terminates active sessions upon logout.

Actor/roles: Registered User (Candidate, Recruiter, Administrator)

Purpose: To authenticate valid users, establish role-based access to protected workspaces, and cleanly invalidate sessions upon departure.

Interface: Web: Account Login

Data processing:

  • Input data: Email address, password, optional two-factor one-time verification code (if 2FA is active).
  • Output data: Authenticated user session, role-scoped routing redirect (Candidate Dashboard, Recruiter Dashboard, or Admin Governance Console), or invalidated session state.

Function details: The system handles credential verification, authentication, and secure session persistence. When an account has two-factor authentication enabled, the system enforces a secondary verification challenge before issuing the session. If an account is locked by platform administration, authentication is blocked immediately.

Business rule: BR-04 (A user must be authenticated before accessing registered-user features), BR-05 (A locked account must not be allowed to log in or access protected functions), BR-08 (When two-factor authentication is enabled for an account, authentication is not complete until the two-factor challenge is verified).

Normal case:

  1. The user navigates to the Account Login screen and enters their email and password.
  2. The system verifies that the credentials are valid and confirms the account is not locked (BR-05).
  3. (If 2FA is enabled) The system prompts for the two-factor authentication code and verifies it (BR-08).
  4. The system establishes an authenticated session (BR-04) and redirects the user to their respective role dashboard.
  5. (Upon Logout) The authenticated user clicks the Logout action; the system invalidates the session and redirects to the Public Landing Page.

Abnormal case:

  • Invalid credentials: The system displays an authentication error without revealing whether the email or password was incorrect.
  • Locked account: The system denies access and informs the user that the account has been suspended by platform administration (BR-05).
  • Invalid 2FA code: The system notifies the user of an invalid verification code and permits retry within rate-limiting boundaries.

Screen layout: Screen Layout Reference: Account Login. Visual layout to be produced during the dedicated UI design phase.

3.2.4 Forgot Password & Credential Recovery

Function trigger: An unauthenticated user clicks the "Forgot Password?" link on the Account Login screen.

Function description: This function coordinates the self-service credential recovery process by validating the registered email address, issuing a single-use time-limited reset token, and providing a secure interface to establish a new password compliant with platform complexity standards.

Actor/roles: Registered User

Purpose: To allow users who have forgotten their credentials to regain secure access to their accounts without administrative intervention.

Interface: Web: Forgot Password Request, Password Reset Link Dispatched Notice, Set New Password

Data processing:

  • Input data: Registered email address, single-use reset token, new password, new password confirmation.
  • Output data: Password reset notification email, verified reset authorization, updated password hash.

Function details: In accordance with canonical specifications, password reset does not form an independent Use Case but represents the completion flow of the Forgot Password capability. The recovery token expires after a predefined security duration and is invalidated immediately upon first use.

Business rule: BR-02 (An account password must be between 8 and 32 characters long), BR-03 (An account password must contain at least one lowercase letter, one uppercase letter, one number, and one special character), BR-06 (A user must verify their identity before resetting a forgotten password), BR-07 (A password reset token can only be used only once).

Normal case:

  1. The user navigates to the Forgot Password Request screen and enters their account email address.
  2. The system checks if the email exists in the registry and generates a cryptographically secure, single-use reset token (BR-06).
  3. The system dispatches an email containing the reset link and displays the Password Reset Link Dispatched Notice.
  4. The user clicks the link from their email and arrives at the Set New Password screen.
  5. The user enters a new password conforming to complexity requirements and confirms it.
  6. The system verifies token validity, consumes the token so it cannot be reused (BR-07), updates the password (BR-02, BR-03), and confirms success.

Abnormal case:

  • Email not found: The system displays a generic confirmation message to prevent user enumeration attacks.
  • Expired or previously consumed token: The system informs the user that the reset link is no longer valid (BR-07) and prompts them to request a new recovery link.
  • New password does not meet complexity requirements: The system displays validation errors and requires correction.

Screen layout: Screen Layout Reference: Forgot Password Request, Password Reset Link Dispatched Notice, Set New Password. Visual layout to be produced during the dedicated UI design phase.

3.2.6 Credential Security & Password Modification

Function trigger: An authenticated user clicks the "Change Password" button within the Account Security & Password management settings.

Function description: This function enables authenticated users to proactively change their account password by verifying their existing current password and providing a new password meeting all complexity criteria.

Actor/roles: Registered User

Purpose: To allow users to maintain account hygiene, satisfy security rotation policies, or mitigate potential credential compromise.

Interface: Web: Account Security & Password, Change Password Modal

Data processing:

  • Input data: Current password, new password, new password confirmation.

Function details: The system re-authenticates the user's current password before allowing the update. The new password cannot be identical to the current password and must comply strictly with length and character composition rules.

Business rule: BR-02 (An account password must be between 8 and 32 characters long), BR-03 (An account password must contain at least one lowercase letter, one uppercase letter, one number, and one special character), BR-04 (A user must be authenticated before accessing registered-user features).

Normal case:

  1. The user navigates to Account Security & Password and selects "Change Password".
  2. The Change Password Modal appears.
  3. The user inputs their current password, desired new password, and confirms the new password.
  4. The system validates the current password, verifies new password strength (BR-02, BR-03), and persists the new credential hash.
  5. The modal closes and a confirmation banner is displayed.

Abnormal case:

  • Incorrect current password: The system rejects the change with an authentication failure message.
  • New password matches current password: The system prompts the user to select a distinct new password.
  • New password violates complexity requirements: The system highlights failing criteria.

3.2.7 Two-Factor Authentication Management

Function trigger: An authenticated user clicks "Set Up 2FA" or "Manage 2FA" in the Account Security & Password interface.

Function description: This function manages the configuration of time-based one-time password (TOTP) two-factor authentication, generating a secret seed, rendering a QR code for authenticator application onboarding, and verifying a test code before activating multi-factor enforcement.

Actor/roles: Registered User

Purpose: To provide enhanced account protection against unauthorized access through two-factor authentication.

Interface: Web: Account Security & Password, Two-Factor Authentication Setup Modal

Data processing:

  • Input data: TOTP secret registration request, 6-digit confirmation verification code.
  • Output data: Rendered TOTP QR code, secret key display, 2FA status flag (Enabled/Disabled), backup recovery codes.

Function details: To prevent lockout, 2FA is not permanently activated until the user enters a valid 6-digit code generated from their newly paired authenticator application. Once active, all subsequent logins require passing the 2FA challenge.

Business rule: BR-04 (A user must be authenticated before accessing registered-user features), BR-08 (When two-factor authentication is enabled for an account, authentication is not complete until the two-factor challenge is verified).

Normal case:

  1. The user navigates to Account Security & Password and clicks "Enable Two-Factor Authentication".
  2. The Two-Factor Authentication Setup Modal opens, displaying a QR code and secret text key.
  3. The user scans the QR code with their TOTP authenticator application (e.g., Google Authenticator).
  4. The user inputs the 6-digit token displayed in their authenticator app and clicks "Verify and Enable".
  5. The system confirms code validity, marks 2FA as active on the user's account (BR-08), and presents one-time backup recovery codes.

Abnormal case:

  • Invalid verification code: The system displays a mismatch error and instructs the user to check their device time synchronization and re-enter the code.
  • Modal cancellation before verification: The unconfirmed 2FA configuration is discarded; 2FA remains disabled.

Screen layout: Screen Layout Reference: Account Security & Password, Two-Factor Authentication Setup Modal. Visual layout to be produced during the dedicated UI design phase.

3.3 Candidate Interview Practice Management

This section defines the functional requirements for candidate practice interview operations, encompassing target job description ingestion and AI competency extraction, personal 3D avatar generation, simulation parameter configuration, hardware readiness testing, real-time 3D AI interview execution, session resumption, multi-dimensional diagnostic evaluation, and longitudinal history archiving.

3.3.1 Target JD Ingestion & AI Extraction

Function trigger: A Candidate clicks "Add Target JD" or "Import Job Description" from the Target JD Library.

Function description: This function accepts raw job description text or document uploads from the Candidate, validates the content, triggers an asynchronous AI extraction process to parse structured competency requirements, and stages the draft for Candidate review.

Actor/roles: Candidate

Purpose: To ingest real-world job postings into the platform so that tailored technical interview simulations can be dynamically structured.

Interface: Web: Add Target JD

Data processing:

  • Input data: Raw job description text (pasted text) or uploaded JD document (PDF), target job title.
  • Output data: Validated ingestion payload, staged draft JD record.

Function details: Candidates maintain complete private ownership over their imported Target JDs. The ingestion module ensures the provided content contains sufficient textual depth for competency parsing before submitting it to the LLM extraction pipeline.

Business rule: BR-09 (Candidates can only access and manage their own Target JD for practice), BR-10 (A Candidate must review and confirm the AI-extracted Job Description before the system uses it to generate an Interview Blueprint), BR-13 (A Candidate Target JD for Practice is private Candidate data and is distinct from a Recruiter Job Posting).

Normal case:

  1. The Candidate navigates to the Add Target JD screen.
  2. The Candidate inputs a job title, and pastes the raw job description text or uploads a JD file.
  3. The Candidate submits the form for extraction.
  4. The system validates text content, invokes AI extraction to identify core requirements, tech stacks, and seniority levels, and automatically routes the Candidate to the Review & Refine Extracted JD screen.

Abnormal case:

  • Empty or insufficiently informative JD text (under minimum length threshold): The system prompts the Candidate that the text is too brief to extract technical competencies.
  • Unsupported file upload format: The system alerts the user and limits uploads to supported text/document formats.

Screen layout: Screen Layout Reference: Add Target JD. Visual layout to be produced during the dedicated UI design phase.

3.3.2 Review, Refine & Confirm Extracted Target JD

Function trigger: The AI extraction completes, or the Candidate opens an existing unconfirmed Target JD from their library.

Function description: This function allows the Candidate to inspect the structured competencies extracted by AI, adjust technical domains, add custom refinement notes (such as excluding specific libraries or emphasizing architectural concepts), and formally approve the finalized JD for interview generation.

Actor/roles: Candidate

Purpose: To ensure human verification of AI-extracted technical requirements and allow personalized customization before interview simulations are generated.

Interface: Web: Review & Refine Extracted JD, Refinement Notes Panel

Data processing:

  • Input data: Candidate edits to job title, role level, core skills, responsibilities, optional refinement notes (exclusions/emphases).
  • Output data: Approved Target JD record with finalized competency taxonomy, internal Interview Blueprint readiness trigger.

Function details: Human review is mandatory. Once the Candidate clicks "Approve and Confirm", the Target JD status transitions from Staged to Approved. System internal processes subsequently derive the internal Interview Blueprint (BR-11, BR-12) used by the interview simulator. Per ratified domain rules, the Interview Blueprint remains internal and hidden from the Candidate.

Business rule: BR-09 (Candidates can only access and manage their own Target JD for practice), BR-10 (A Candidate must review and confirm the AI-extracted Job Description before the system uses it to generate an Interview Blueprint), BR-11 (Interview Blueprint generation must use the approved Extracted Job Description, interview configuration, and global Evaluation Criteria), BR-12 (The Interview Blueprint is an internal system artifact and must not be exposed to the Candidate as a visible screen, preview, or manual builder step), BR-13 (A Candidate Target JD for Practice is private Candidate data and is distinct from a Recruiter Job Posting).

Normal case:

  1. The Candidate views the extracted job title, technical stack, core responsibilities, and competencies on the Review & Refine Extracted JD screen.
  2. (Optional) The Candidate opens the Refinement Notes Panel and adds specific guidance (e.g., "Exclude Angular; focus on React and micro-frontends").
  3. The Candidate edits any extracted fields if necessary to match their practice goals.
  4. The Candidate clicks "Approve and Confirm" (BR-10).
  5. The system persists the confirmed Target JD, triggers background preparation of the internal Interview Blueprint (BR-11, BR-12), and presents options to configure a practice session.

Abnormal case:

  • Candidate cancels the review: The system retains the draft Target JD in unconfirmed state; no internal blueprint is generated until approval is given.
  • All competencies cleared: The system prevents approval if the competency taxonomy is completely emptied.

Screen layout: Screen Layout Reference: Review & Refine Extracted JD, Refinement Notes Panel. Visual layout to be produced during the dedicated UI design phase.

Function details: Candidates can only access their own private JDs. Deletion removes the Target JD record from the library, but in accordance with data integrity rules (BR-14), all previously completed interview sessions and performance reports linked to that JD remain fully intact and accessible in the Candidate's history.

Business rule: BR-09 (Candidates can only access and manage their own Target JD for practice), BR-13 (A Candidate Target JD for Practice is private Candidate data and is distinct from a Recruiter Job Posting), BR-14 (Deleting a saved Target JD must not invalidate historical completed Interview Sessions or their attached Performance Reports).

Normal case:

  6. The system removes the JD from the active library while preserving any historical interview reports linked to it (BR-14).

Abnormal case:

3.3.4 Personal 3D Avatar Generation

Function trigger: A Candidate clicks "Create 3D Avatar" or "Generate Personal Avatar" within the Personal 3D Avatar Studio.

Function description: This function integrates an embedded Avaturn web experience allowing the Candidate to capture photos, preview and customize a personal 3D avatar, and hand off the generated GLB asset to RoleCue for conversion to VRM and private candidate storage.

Actor/roles: Candidate

Purpose: To enable candidates to embody a realistic personal 3D avatar during interactive interview simulations.

Interface: Web: Personal 3D Avatar Studio, Avaturn Embedded Experience, Personal Avatar Confirmation & Preview

Data processing:

  • Input data: Captured user photo, user hairstyle/clothing selections within Avaturn iframe, generated GLB export payload.
  • Output data: Processed and validated VRM avatar model, avatar metadata record, updated candidate avatar library.

Function details: As ratified in architectural decisions, the personal avatar flow utilizes the free embedded Avaturn iframe rather than a paid Pro API. Avaturn handles image capture, photo quality checks, facial reconstruction, and GLB export. When Avaturn completes generation, RoleCue receives the GLB file, converts it into a standard VRM avatar model with facial blendshapes, and binds it strictly to the owning Candidate. If conversion fails, the avatar is not made available.

Business rule: BR-18 (A Personal 3D Avatar generated from a Candidate's photo belongs to that Candidate and is private Candidate data), BR-53 (Photo capture, photo validation, avatar preview, customization, and GLB generation are handled by the embedded Avaturn experience), BR-54 (The Personal 3D Avatar generation flow must not depend on Avaturn Pro API orchestration), BR-55 (RoleCue may persist a newly generated Personal 3D Avatar only after receiving the completed GLB asset from the embedded Avaturn flow), BR-56 (If GLB-to-VRM conversion fails, the Personal 3D Avatar must not be marked as available for Candidate use), BR-57 (A Candidate-owned Personal 3D Avatar must only be accessible to its owning Candidate).

Normal case:

  1. The Candidate navigates to the Personal 3D Avatar Studio and clicks "Generate Avatar".
  2. The system loads the Avaturn Embedded Experience within a secure iframe (BR-53, BR-54).
  3. The Candidate follows Avaturn's instructions to take or upload a front-facing selfie.
  4. Avaturn reconstructs the 3D head mesh and allows the Candidate to select clothing and hairstyles.
  5. The Candidate confirms the avatar, and Avaturn exports the final GLB asset.
  6. RoleCue captures the GLB payload (BR-55), converts it to VRM format, verifies facial blendshapes, and saves it to the Candidate's profile (BR-18, BR-57).
  7. The system redirects to the Personal Avatar Confirmation & Preview screen where the Candidate inspects the interactive 3D model.

Abnormal case:

  • Poor photo quality / face not recognized: Avaturn prompts the user within the iframe to re-capture under better lighting (BR-53).
  • Conversion failure (corrupt GLB or invalid blendshapes): RoleCue detects the conversion failure (BR-56), discards the invalid asset, and notifies the Candidate to retry.
  • Candidate closes the iframe before completing export: The session terminates cleanly without persisting an incomplete avatar.

Screen layout: Screen Layout Reference: Personal 3D Avatar Studio, Avaturn Embedded Experience, Personal Avatar Confirmation & Preview. Visual layout to be produced during the dedicated UI design phase.

Abnormal case:

3.3.7 Interactive 3D AI Interview Simulation

Function trigger: The Candidate passes the readiness preflight and clicks "Join Interview Room".

Function description: This function conducts the real-time technical interview simulation. It renders the 3D virtual interviewer avatar in the selected room environment, orchestrates spoken question delivery via text-to-speech with synchronized viseme lip-sync, captures Candidate speech via real-time speech-to-text, and allows the dynamic LLM runtime to evaluate answers and determine subsequent questions until session conclusion.

Actor/roles: Candidate, AI Virtual Interviewer (System)

Purpose: To simulate an authentic technical interview experience with visual and auditory realism, allowing candidates to practice under realistic conditions.

Interface: Web: Live 3D Interview Room, Interview Session Pause / Exit Modal, 2D Waveform Fallback View

Data processing:

  • Input data: Candidate live microphone stream, pause/exit user actions.
  • Output data: Transcribed Candidate answer text, synthesized 3D interviewer speech audio, synchronized facial blendshape animation, dynamic question dialogue turns, completed transcript record.

Function details: The 3D interviewer avatar performs natural idle animations and viseme-driven lip-sync during speech. Candidate spoken answers are transcribed into text. At product level, the dialogue consists of generic Questions delivered sequentially (BR-58). The LLM runtime determines whether an answer is sufficient or requires further questioning before concluding the interview. If WebGL experiences GPU memory exhaustion or fails, the interface gracefully degrades to the 2D Waveform Fallback View without terminating the session.

Business rule: BR-15 (An Interview Session can only start only after the relevant Extracted Job Description is approved and confirmed), BR-47 (A Candidate interviewing for a Recruiter Job Posting must use the 3D interviewer model specified by the Recruiter), BR-48 (A Candidate interviewing for a Recruiter Job Posting must use the Voice Profile specified by the Recruiter), BR-58 (An interview proceeds to evaluation when the interview engine determines that no further questions are required).

Normal case:

  1. The Candidate enters the Live 3D Interview Room (UC 15).
  2. The 3D virtual interviewer welcomes the Candidate and delivers the first Question using synthesized speech with lip-sync.
  3. The Candidate speaks their answer; the system captures audio and transcribes the speech (UC 16).
  4. The system runtime analyzes the response and determines the next question turn.
  5. Steps 2–4 repeat dynamically across relevant technical competencies.
  6. When the interview engine determines that all required topics have been covered (BR-58), the interviewer announces the conclusion of the interview.
  7. The system transitions the session to "Evaluating" status and automatically routes the Candidate to the performance evaluation screen.

Abnormal case:

  • Candidate clicks "Pause / Exit": The Interview Session Pause / Exit Modal appears, allowing the Candidate to pause the session or exit cleanly.
  • Hardware/WebGL crash: The system activates the 2D Waveform Fallback View, allowing the Candidate to continue the interview via audio only.
  • Abrupt browser closure / disconnect: The session enters "Interrupted" state, awaiting resumption within the allowable timeout window (BR-19, BR-20).

  • Output data: Restored live interview context and dialogue state, or finalized "Abandoned" session status with resource cleanup.

Business rule: BR-19 (A Candidate can only resume an interrupted Interview Session only while that session remains in an active or resumable state), BR-20 (If a Candidate leaves or remains disconnected from an Interview Session for more than 15 minutes, the system must terminate the session as abandoned).

  5. (System Abandonment Termination - UC 57) An interrupted session exceeds 15 minutes of continuous disconnection.
  6. The background System Handler identifies the stale session, marks it as "Abandoned" (BR-20), invalidates the live runtime token, and records the abandonment event.

Abnormal case:

  • Candidate attempts to resume after 15 minutes: The system informs the Candidate that the session has expired and cannot be resumed; the Candidate must initiate a new practice session (BR-20).

Changes take effect for newly initiated interview sessions while preserving historical consistency for completed sessions. The Prompt Template Editor Drawer allows adjusting interviewer tone and follow-up strictness, while the Rubric Template Editor Drawer allows calibrating criteria weighting (e.g., technical correctness, architecture design, clarity).

Business rule: BR-37 (Only an Administrator can edit global Evaluation Criteria), BR-38 (Only an Administrator can manage platform AI Behaviour and interview-feature configurations).

Normal case:

  1. The Administrator accesses AI Behaviour Management and opens the Prompt Template Editor Drawer (UC 46).
  2. The Administrator adjusts interviewer conversational behavior instructions and saves changes.
  3. The Administrator opens Evaluation Criteria Calibration and launches the Rubric Template Editor Drawer (UC 45).
  4. The Administrator updates competency weighting parameters and confirms validation checks.
  5. The system saves the calibrated rubric version (BR-37, BR-38) and applies it to subsequent interview sessions.

Abnormal case:

  • Scoring weights do not sum to 100%: The system flags the validation discrepancy and prevents saving until weights are balanced.

Screen layout: Screen Layout Reference: Interview Feature Configuration, AI Behaviour Management, Prompt Template Editor Drawer, Evaluation Criteria Calibration, Rubric Template Editor Drawer. Visual layout to be produced during the dedicated UI design phase.

3.5.5 Provider Voice Profile Catalog Management

Function trigger: An Administrator navigates to the Voice Profile Catalog in the governance console.

Function description: This function manages the catalog of available text-to-speech voice profiles by fetching external voice assets from the connected provider (e.g., ElevenLabs), cataloging voice metadata (gender, accent, language), and deprecating or removing outdated voice profiles.

Actor/roles: Administrator, External TTS Provider (ElevenLabs)

Purpose: To curate a high-quality selection of realistic voices available for candidate practice and recruiter job opening configurations.

Interface: Web: Voice Profile Catalog, Fetch Voice Profiles Modal, Delete Voice Profile Dialog

Data processing:

  • Input data: Fetch provider trigger, provider API synchronization parameters, Voice Profile ID selected for deletion/deactivation.
  • Output data: Synchronized voice catalog list, updated voice metadata records, deletion confirmation.

Function details: Administrators manage provider-sourced Voice Profiles (BR-39). In accordance with ratified product scope, Administrators do NOT manage candidate 3D avatars or virtual room backgrounds (BR-40). Fetching voices queries the external TTS provider and registers available voice IDs. Deleting a voice profile marks it as unavailable for future sessions while preserving historical references in completed interview logs.

Business rule: BR-39 (Only an Administrator can fetch, view, or delete provider-sourced Voice Profiles), BR-40 (Administrators must not manage Candidate Personal 3D Avatar assets or the platform 3D background catalog).

Normal case:

  1. The Administrator navigates to the Voice Profile Catalog.
  2. The system displays all registered voice profiles with name, provider ID, accent, and sample audio playback (UC 47).

  4. The system queries the external TTS provider API, identifies newly available voices, and synchronizes the catalog.
  5. (Optional) The Administrator selects an obsolete voice profile, clicks "Delete", and confirms via the Delete Voice Profile Dialog (UC 49).
  6. The system removes or deactivates the voice profile (BR-39).

Abnormal case:

  • Provider API connection timeout: The system displays a connectivity alert and retains the existing voice catalog without corruption.
  • Attempting to delete a voice currently configured on an active published job posting: The system warns the Administrator and requires reassignment or soft-deprecation.

3.6 Membership & Payment Management

This section defines the functional requirements for candidate subscription billing, secure third-party payment gateway checkout, financial transaction audit ledgering, platform revenue analytics, and administrative subscription tier pricing governance.

3.6.1 Candidate Membership Subscription & Cancellation

Function trigger: A Candidate clicks "Subscribe Membership" or "Manage Subscription" on the Membership & Billing screen.

Function description: This function manages the Candidate membership subscription lifecycle, directing the user to a secure payment gateway for checkout, activating paid Membership benefits upon successful payment confirmation, and processing voluntary cancellation requests.

Actor/roles: Candidate, External Payment Gateway

Purpose: To provide candidates with access to paid platform features through secure subscription transactions.

Interface: Web: Membership & Billing, Payment Gateway Checkout Redirect, Unsubscribe Confirmation Dialog

Data processing:

  • Input data: Selected Membership plan, billing cycle, payment gateway callback payload, cancellation confirmation.
  • Output data: Initialized checkout session URL, updated membership status (Active / Inactive / Canceled), billing renewal date.

Function details: In alignment with ratified domain decisions, RoleCue operates strictly on a recurring subscription membership model. Paid membership benefits are strictly activated only after the payment gateway confirms successful transaction completion (BR-42). If a payment is pending or fails, benefits are not granted (BR-43). When a Candidate cancels their subscription, benefits remain active until the end of the paid billing period.

Business rule: BR-42 (A paid Membership state must be activated or updated only after the associated payment transaction succeeds), BR-43 (A failed or pending payment must not grant paid Membership benefits, and the same payment attempt cannot activate benefits more than once).

Normal case:

  1. The Candidate navigates to the Membership & Billing screen and selects a subscription plan.
  2. The system initializes a transaction record and redirects the Candidate via the Payment Gateway Checkout Redirect screen to the external payment gateway.
  3. The Candidate completes payment authorization on the secure provider portal.
  4. The payment gateway returns a verified success callback to RoleCue.
  5. The system confirms the transaction, activates the paid Membership state on the Candidate's account (BR-42), and updates the billing dashboard.
  6. (Cancellation) An active subscriber clicks "Cancel Subscription" on the Membership & Billing screen.
  7. The Unsubscribe Confirmation Dialog appears, outlining benefit expiration details at the end of the billing term.
  8. The Candidate confirms cancellation; the system updates the renewal status, preventing future renewals while maintaining access until period end.

Abnormal case:

  • Payment declined or canceled by user: The payment gateway returns a failure/cancel callback; the system leaves the account in the inactive membership state (BR-43) and displays a payment failed message.
  • Duplicate callback / replay: The system detects that the transaction has already been settled and ignores redundant activations (BR-43).

Screen layout: Screen Layout Reference: Membership & Billing, Payment Gateway Checkout Redirect, Unsubscribe Confirmation Dialog. Visual layout to be produced during the dedicated UI design phase.

3.6.2 Financial Transactions Audit & Revenue Reporting

Function trigger: An Administrator navigates to "Payment Transactions Ledger" or "Revenue Report Generator", or a Candidate views their personal payment history.

Function description: This function maintains an immutable audit ledger of all platform membership payment transactions, allows searching and filtering transactions by date and status, and generates aggregated financial revenue reports.

Actor/roles: Administrator (for global ledger and revenue reports), Candidate (for personal transaction history)

Purpose: To ensure financial transparency, audit payment gateway reconciliation, and analyze recurring platform revenue.

Interface: Web: Payment Transactions Ledger, Revenue Report Generator, Payment Transaction History

Data processing:

  • Input data: Date range filters, transaction status filters (Success, Failed, Refunded), report grouping parameters (Monthly, Quarterly).
  • Output data: Filtered transaction ledger table, aggregated revenue figures, exportable revenue summary reports.

Function details: Administrators have access to view all payment transactions across the platform and generate executive revenue summaries (BR-41). Candidates can view their own personal historical transactions via Payment Transaction History. All transaction records are read-only and reconciled against external gateway reference identifiers.

Business rule: BR-41 (Only Administrators can update Membership pricing and view platform Payment Transactions or generate Revenue Reports).

Normal case:

  1. The Administrator navigates to the Payment Transactions Ledger in the governance console.
  2. The system renders all platform payment transactions with user email, gateway transaction ID, amount, and status (UC 52, BR-41).
  3. The Administrator filters records by date range or transaction status.
  4. The Administrator opens the Revenue Report Generator (UC 53).
  5. The Administrator selects reporting parameters (e.g., Monthly revenue breakdown) and clicks "Generate Report".
  6. The system calculates total gross revenue, transaction counts, and churn rates, displaying the interactive summary with export options.

Abnormal case:

  • Non-admin user attempts to access administrative revenue reports: Access is denied (BR-41).

Screen layout: Screen Layout Reference: Payment Transactions Ledger, Revenue Report Generator, Payment Transaction History. Visual layout to be produced during the dedicated UI design phase.

3.6.3 Membership Pricing Governance

Function trigger: An Administrator clicks "Update Pricing" on the membership configuration view within the governance console.

Function description: This function allows administrators to update the subscription fee and billing terms for platform membership tiers, establishing new baseline pricing for upcoming subscriber sign-ups.

Actor/roles: Administrator

Purpose: To manage platform commercial packaging and adjust subscription price points in accordance with business strategy.

Interface: Web: Membership & Billing, Update Membership Price Modal

Data processing:

  • Input data: Membership plan ID, new subscription price, effective currency, administrative confirmation.
  • Output data: Updated membership pricing schedule, pricing audit log record.

Function details: Only Administrators possess the authority to modify membership prices (BR-41). Updating a plan's price applies to new subscription checkouts in accordance with platform policy.

Business rule: BR-41 (Only Administrators can update Membership pricing and view platform Payment Transactions or generate Revenue Reports).

Normal case:

  1. The Administrator opens the membership configuration panel and selects "Update Membership Price".
  2. The Update Membership Price Modal opens, displaying current Membership pricing.
  3. The Administrator enters the new subscription fee and clicks "Save Changes".
  4. The system verifies administrator authorization (BR-41), validates that the price is a positive monetary value, and persists the new price.
  5. The updated price is immediately reflected in the checkout flow.

Abnormal case:

  • Invalid or negative price input: The system rejects the value and prompts for a valid numerical price.
  • Unauthorized user attempt: Access blocked with permission violation.

Screen layout: Screen Layout Reference: Membership & Billing, Update Membership Price Modal. Visual layout to be produced during the dedicated UI design phase.
