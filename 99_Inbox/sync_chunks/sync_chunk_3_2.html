3.2 Account & Access Management

This section defines the functional requirements for user registration, identity authentication, credential recovery, user profile management, credential security, and multi-factor authentication across all platform user roles.

3.2.1 Platform Public Exploration & Value Proposition

Function trigger: A Guest accesses the platform root URL via a web browser.

Function description: This function renders the public marketing and platform introduction portal, showcasing the RoleCue value proposition, technical interview simulation capabilities, supported industry domains, and navigation paths for account registration and authentication.

Actor/roles: Guest

Purpose: To introduce prospective candidates and recruiters to the platform's AI-driven technical interview features and facilitate user onboarding.

Interface: Web: Public Landing Page

Data processing:

  • Input data: HTTP request parameters, public catalog highlights, feature overview assets.
  • Output data: Rendered public landing view, product overview summaries, navigation links to registration and login.

Function details: The interface operates publicly without requiring prior authentication. It presents overview highlights regarding real-time 3D interviewer interaction, job description analysis, automated rubric-based scoring, and recruiting capabilities.

Business rule: BR-04 (A user must be authenticated before accessing registered-user features; unauthenticated guests may only view public marketing content and entry points).

Normal case:

  1. The Guest navigates to the platform base URL.
  2. The system loads and displays the Public Landing Page with feature highlights, value propositions, and role-based onboarding calls to action.
  3. The Guest clicks the registration or login call to action to transition to the respective authentication interface.

Abnormal case:

  • Network connectivity failure prevents assets from loading; the client renders an offline retry notice.

Screen layout: Screen Layout Reference: Public Landing Page. Visual layout to be produced during the dedicated UI design phase.

3.2.2 User Registration & Role Selection

Function trigger: A Guest clicks the "Sign Up" or "Register" button on the Public Landing Page or login view.

Function description: This function captures account registration credentials, validates email uniqueness and password complexity, establishes the initial user identity record, and dispatches an email verification notice.

Actor/roles: Guest

Purpose: To allow new candidates and recruiters to establish authenticated accounts with verified identities and defined roles.

Interface: Web: Account Registration, Email Verification Notice

Data processing:

  • Input data: Full name, email address, password, password confirmation, desired account role (Candidate or Recruiter).
  • Output data: Newly created user account record with pending verification status, dispatched verification token, and confirmation screen.

Function details: Registration validates that the provided email is not already associated with an existing account. The system validates password strength according to platform security policy. Better Auth manages the underlying credential generation and token creation, while the interface transitions the user to the Email Verification Notice screen.

Business rule: BR-01 (An account must have a unique email address), BR-02 (An account password must be between 8 and 32 characters long), BR-03 (An account password must contain at least one lowercase letter, one uppercase letter, one number, and one special character).

Normal case:

  1. The Guest navigates to the Account Registration screen.
  2. The Guest inputs their full name, email address, password, password confirmation, and selects their role.
  3. The system validates that the email address is unique and the password complies with security rules.
  4. The system registers the account in a pending verification state and sends an email containing an activation link.
  5. The system redirects the user to the Email Verification Notice screen with instructions to check their inbox.

Abnormal case:

  • Duplicate email address: The system informs the user that an account with this email already exists and offers a link to login or recover the password (BR-01).
  • Password complexity violation: The system indicates the specific unmet requirements (length, case, numeric, or special character) and prevents submission (BR-02, BR-03).
  • Confirmation password mismatch: The system flags the mismatch and prompts the user to re-enter matching passwords.

Screen layout: Screen Layout Reference: Account Registration, Email Verification Notice. Visual layout to be produced during the dedicated UI design phase.

3.2.3 User Authentication & Session Resolution

Function trigger: A user submits login credentials on the Account Login screen, or clicks the "Sign Out" action from the authenticated navigation bar.

Function description: This function verifies user identity via email and password credentials, checks account status against governance restrictions, prompts for two-factor authentication if enabled, resolves an authenticated session, and terminates active sessions upon logout.

Actor/roles: Registered User (Candidate, Recruiter, Administrator)

Purpose: To authenticate valid users, establish role-based access to protected workspaces, and cleanly invalidate sessions upon departure.

Interface: Web: Account Login

Data processing:

  • Input data: Email address, password, optional two-factor one-time verification code (if 2FA is active).
  • Output data: Authenticated user session, role-scoped routing redirect (Candidate Dashboard, Recruiter Dashboard, or Admin Governance Console), or invalidated session state.

Function details: Better Auth handles credential verification, session token generation, and secure session persistence. When an account has two-factor authentication enabled, the system enforces a secondary verification challenge before issuing the session. If an account is locked by platform administration, authentication is blocked immediately.

Business rule: BR-04 (A user must be authenticated before accessing registered-user features), BR-05 (A locked account must not be allowed to log in or access protected functions), BR-08 (When two-factor authentication is enabled for an account, authentication is not complete until the two-factor challenge is verified).

Normal case:

  1. The user navigates to the Account Login screen and enters their email and password.
  2. The system verifies that the credentials are valid and confirms the account is not locked (BR-05).
  3. (If 2FA is enabled) The system prompts for the two-factor authentication code and verifies it (BR-08).
  4. The system establishes an authenticated session (BR-04) and redirects the user to their respective role dashboard.
  5. (Upon Logout) The authenticated user clicks the Logout action; the system invalidates the session and redirects to the Public Landing Page.

Abnormal case:

  • Invalid credentials: The system displays an authentication error without revealing whether the email or password was incorrect.
  • Locked account: The system denies access and informs the user that the account has been suspended by platform administration (BR-05).
  • Invalid 2FA code: The system notifies the user of an invalid verification code and permits retry within rate-limiting boundaries.

Screen layout: Screen Layout Reference: Account Login. Visual layout to be produced during the dedicated UI design phase.

3.2.4 Forgot Password & Credential Recovery

Function trigger: An unauthenticated user clicks the "Forgot Password?" link on the Account Login screen.

Function description: This function coordinates the self-service credential recovery process by validating the registered email address, issuing a single-use time-limited reset token, and providing a secure interface to establish a new password compliant with platform complexity standards.

Actor/roles: Registered User

Purpose: To allow users who have forgotten their credentials to regain secure access to their accounts without administrative intervention.

Interface: Web: Forgot Password Request, Password Reset Link Dispatched Notice, Set New Password

Data processing:

  • Input data: Registered email address, single-use reset token, new password, new password confirmation.
  • Output data: Password reset notification email, verified reset authorization, updated password hash.

Function details: In accordance with canonical specifications, password reset does not form an independent Use Case but represents the completion flow of the Forgot Password capability. The recovery token expires after a predefined security duration and is invalidated immediately upon first use.

Business rule: BR-02 (An account password must be between 8 and 32 characters long), BR-03 (An account password must contain at least one lowercase letter, one uppercase letter, one number, and one special character), BR-06 (A user must verify their identity before resetting a forgotten password), BR-07 (A password reset token can only be used only once).

Normal case:

  1. The user navigates to the Forgot Password Request screen and enters their account email address.
  2. The system checks if the email exists in the registry and generates a cryptographically secure, single-use reset token (BR-06).
  3. The system dispatches an email containing the reset link and displays the Password Reset Link Dispatched Notice.
  4. The user clicks the link from their email and arrives at the Set New Password screen.
  5. The user enters a new password conforming to complexity requirements and confirms it.
  6. The system verifies token validity, consumes the token so it cannot be reused (BR-07), updates the password (BR-02, BR-03), and confirms success.

Abnormal case:

  • Email not found: The system displays a generic confirmation message to prevent user enumeration attacks.
  • Expired or previously consumed token: The system informs the user that the reset link is no longer valid (BR-07) and prompts them to request a new recovery link.
  • New password does not meet complexity requirements: The system displays validation errors and requires correction.

Screen layout: Screen Layout Reference: Forgot Password Request, Password Reset Link Dispatched Notice, Set New Password. Visual layout to be produced during the dedicated UI design phase.

3.2.5 Profile Inspection & Update

Function trigger: An authenticated user clicks on their user avatar or selects "Profile" from the top navigation header.

Function description: This function presents the user's personal identity and contact details, and enables self-service editing of editable profile attributes such as display name, headline, phone number, bio, and avatar portrait.

Actor/roles: Registered User (Candidate, Recruiter, Administrator)

Purpose: To allow users to maintain up-to-date personal and professional identity information across the platform.

Interface: Web: User Profile

Data processing:

  • Input data: Updated display name, phone number, professional title/headline, biographical summary, profile image upload.
  • Output data: Refreshed user profile record, persisted profile image asset, updated display in the application shell.

Function details: Users can only view and update their own personal profile records. Read-only fields include account creation timestamp, verified email address (managed through dedicated security workflows), and assigned platform role.

Business rule: BR-04 (A user must be authenticated before accessing registered-user features).

Normal case:

  1. The user navigates to the User Profile screen (UC 5).
  2. The system displays current profile information, including name, email, role, and profile portrait.
  3. The user modifies editable fields (e.g., changes display name or uploads a new portrait) and clicks "Save Changes" (UC 6).
  4. The system validates the inputs, updates the profile in the user repository, and displays a success notification.

Abnormal case:

  • Invalid file format or oversized avatar image: The system rejects the upload with an informative validation message.
  • Missing mandatory field: The system flags required fields that have been cleared and prevents submission.

Screen layout: Screen Layout Reference: User Profile. Visual layout to be produced during the dedicated UI design phase.

3.2.6 Credential Security & Password Modification

Function trigger: An authenticated user clicks the "Change Password" button within the Account Security & Password management settings.

Function description: This function enables authenticated users to proactively change their account password by verifying their existing current password and providing a new password meeting all complexity criteria.

Actor/roles: Registered User

Purpose: To allow users to maintain account hygiene, satisfy security rotation policies, or mitigate potential credential compromise.

Interface: Web: Account Security & Password, Change Password Modal

Data processing:

  • Input data: Current password, new password, new password confirmation.
  • Output data: Updated password credential hash, audit timestamp of password modification.

Function details: The system re-authenticates the user's current password before allowing the update. The new password cannot be identical to the current password and must comply strictly with length and character composition rules.

Business rule: BR-02 (An account password must be between 8 and 32 characters long), BR-03 (An account password must contain at least one lowercase letter, one uppercase letter, one number, and one special character), BR-04 (A user must be authenticated before accessing registered-user features).

Normal case:

  1. The user navigates to Account Security & Password and selects "Change Password".
  2. The Change Password Modal appears.
  3. The user inputs their current password, desired new password, and confirms the new password.
  4. The system validates the current password, verifies new password strength (BR-02, BR-03), and persists the new credential hash.
  5. The modal closes and a confirmation banner is displayed.

Abnormal case:

  • Incorrect current password: The system rejects the change with an authentication failure message.
  • New password matches current password: The system prompts the user to select a distinct new password.
  • New password violates complexity requirements: The system highlights failing criteria.

Screen layout: Screen Layout Reference: Account Security & Password, Change Password Modal. Visual layout to be produced during the dedicated UI design phase.

3.2.7 Two-Factor Authentication Management

Function trigger: An authenticated user clicks "Set Up 2FA" or "Manage 2FA" in the Account Security & Password interface.

Function description: This function manages the configuration of time-based one-time password (TOTP) two-factor authentication, generating a secret seed, rendering a QR code for authenticator application onboarding, and verifying a test code before activating multi-factor enforcement.

Actor/roles: Registered User

Purpose: To provide enhanced account protection against unauthorized access through two-factor authentication.

Interface: Web: Account Security & Password, Two-Factor Authentication Setup Modal

Data processing:

  • Input data: TOTP secret registration request, 6-digit confirmation verification code.
  • Output data: Rendered TOTP QR code, secret key display, 2FA status flag (Enabled/Disabled), backup recovery codes.

Function details: To prevent lockout, 2FA is not permanently activated until the user enters a valid 6-digit code generated from their newly paired authenticator application. Once active, all subsequent logins require passing the 2FA challenge.

Business rule: BR-04 (A user must be authenticated before accessing registered-user features), BR-08 (When two-factor authentication is enabled for an account, authentication is not complete until the two-factor challenge is verified).

Normal case:

  1. The user navigates to Account Security & Password and clicks "Enable Two-Factor Authentication".
  2. The Two-Factor Authentication Setup Modal opens, displaying a QR code and secret text key.
  3. The user scans the QR code with their TOTP authenticator application (e.g., Google Authenticator).
  4. The user inputs the 6-digit token displayed in their authenticator app and clicks "Verify and Enable".
  5. The system confirms code validity, marks 2FA as active on the user's account (BR-08), and presents one-time backup recovery codes.

Abnormal case:

  • Invalid verification code: The system displays a mismatch error and instructs the user to check their device time synchronization and re-enter the code.
  • Modal cancellation before verification: The unconfirmed 2FA configuration is discarded; 2FA remains disabled.

Screen layout: Screen Layout Reference: Account Security & Password, Two-Factor Authentication Setup Modal. Visual layout to be produced during the dedicated UI design phase.
